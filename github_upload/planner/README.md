## 6 时间不足反例

另设 D 报告、E 习题、F 阅读笔记，各需 3 小时，均在 10 月 14 日周三 18:00 截止，优先级依次为高、中、低。截止前只有周一 16:00–17:00、周二 10:00–11:00 和 15:00–16:00 三个空档，共 **3 小时**。

| 任务 | 需要时间 | 已安排 | 未安排 |
| --- | --- | --- | --- |
| D 报告 | 3 小时 | 3 小时 | 0 |
| E 习题 | 3 小时 | 0 | 3 小时 |
| F 阅读笔记 | 3 小时 | 0 | 3 小时 |
| 合计 | 9 小时 | 3 小时 | 6 小时 |

因为需求 9 小时大于全部可用容量 3 小时，任何完整计划都至少缺 **6 小时**。参考部分计划把三个一小时空档分给 D。学生应看到：“截止前只有 3 小时可用，E 和 F 各有 3 小时未安排。请增加可用时间、调整工作量，或自行联系相关人员讨论延期。”

系统不得通过撞课、凌晨学习或排到截止之后来凑出完整计划，也不能自动联系老师。贪心策略在其他例子中排不完时，只能说明当前策略有未排工作量；没有容量证据时不能把它称为数学意义上的无解。

## 7 排程规则与默认值

| 规则 | 类型 | 第一版约定 |
| --- | --- | --- |
| 确认后排程 | 硬约束 | 截止日期、具体时刻、时区、剩余用时都明确且经学生确认 |
| 不撞课、不重叠 | 硬约束 | 建议段避开课程、会议、固定安排、锁定段和其他建议段 |
| 不安排过去或截止后 | 硬约束 | `start >= now` 且 `end <= due_at` |
| 合理学习时段 | 硬约束 | 默认 09:00–22:00，学生可缩窄；第一版不扩展到凌晨 |
| 每日专注学习上限 | 硬约束 | 默认 180 分钟，包括当天已完成和未来锁定的学习段 |
| 控制连续学习 | 硬约束 | 连续最多 90 分钟，之后至少留 15 分钟间隔 |
| 截止前缓冲 | 优先目标 | 尽量提前 24 小时完成；不足时允许合法安排并显示 `LOW_BUFFER` |
| 稳定优先顺序 | 初始策略 | 截止时间从早到晚，再按优先级，再按任务 ID |
| 时间不足 | 必需输出 | 每项任务返回未排分钟数和原因 |
| 重新排程 | 硬约束 | 保留已完成和锁定段；显示未来建议的变化，由学生确认保存 |

默认值是 4 号的提议，需全组确认，不是老师指定值。预计用时向上取整到 15 分钟，例如 50 分钟预留 60 分钟，并显示取整差额。可用时段开始向后、结束向前取整，占用时段反向取整；不能因取整侵占课程或越过截止。

## 8 架构位置与实现交接

```mermaid
flowchart LR
    S[公告 邮件 PDF] --> L[LLM 提取任务]
    L --> H[学生确认日期与用时]
    H --> P[排程规则工具 4号与5号]
    A[学生空闲时间和日历占用] --> P
    P --> V[预览  未排工作量  警告]
    V --> C[学生确认后保存内部计划]
```

LLM 理解文字，规则工具负责时间计算和约束检查。排程模块只接收结构化任务和占用区间，不需要完整邮件正文或私人会议标题。初始支持手动可用时间；日历 API 接入由技术同学确认权限与实现。Canvas / LMS 不接入项目。

### 输入与输出

| 输入字段 | 含义 |
| --- | --- |
| `now`、`timezone` | 固定测试时钟和 IANA 学生时区；时间字符串带 UTC 偏移量 |
| `tasks[]` | 唯一 ID、标题、`due_at`、`remaining_minutes`、`priority`、`confirmed` |
| `availability[]` | 学生允许学习的时间段，采用 `[start, end)` |
| `busy[]` | 课程和会议占用区间，结束恰好等于学习开始不算重叠 |
| `completed_blocks[]` | 已完成学习段，不再安排，但计入发生当天的学习上限 |
| `locked_blocks[]` | 未来锁定学习段，不移动，计入任务剩余量和日上限 |
| `settings` | 日上限、学习窗口、单段长度、粒度、缓冲等统一配置 |

输出应有 `status`、`blocks[]`、`unscheduled[]`、`task_results[]`、`warnings[]`。`task_results` 记录原始预计、取整预留、锁定未来、新排和未排分钟数，必须满足：

```text
新排分钟数 + 锁定未来分钟数 + 未排分钟数 = 取整后的剩余工作量
```

`remaining_minutes` 表示尚未完成的工作量，因此已锁定但未完成的未来时段要先扣除，避免重复安排。缺失日期、不确认、过期截止、时间不足、缓冲不足、锁定冲突分别返回明确提示。`complete` 代表有效任务全部排完，不代表没有风险提示。

### 初始实现步骤

1. 校验和规范输入，缺日期或未确认任务返回待处理原因。
2. 把学生空闲时间与学习窗口取交集，扣除过去、课程、会议和锁定段。
3. 按截止、优先级和 ID 排序。先用截止前 24 小时的合法空档，再尝试临近截止空档。
4. 每次增加学习段时检查每日额度、连续时长、休息间隔及截止时间。
5. 返回未排工作量和警告；保存前运行独立检查，不静默覆盖旧计划。

第一版采用可解释的贪心方法。它可能错过某些可行方案，应保留反例改进；不能通过放宽硬约束掩盖问题。

### 重新排程例子

周三 16:00–17:00 临时增加会议后，把 C 的未锁定学习段移到 17:00–18:00；周四 09:00–10:00 的锁定段不变。C 尚需 120 分钟，其中 60 分钟已经锁定，只新增 60 分钟。如果锁定段本身与新会议冲突，提示用户处理，不能自动移走锁定段。

## 9 当前检查结果与运行方法

五个虚构开发案例为：正常一周、容量不足、缓冲不足、日期待确认、临时会议重新排程。当前 **5/5 手排参考方案通过检查**，且 **5/5 故意错误输出触发预期检查**：凌晨安排、截止后安排、双重预约、隐藏缺口、移动锁定段。

这些成绩属于手排方案和检查器，不是自动排程程序的准确率，不是独立评估，也不是用户研究。故意错误输出不是最终报告中的真实系统失败案例。

在本目录运行：

```bash
python -m pip install -r requirements.txt
python check_reference_cases.py --write-report
```

需要 Python 3.9+。脚本读取本目录案例，检查约束和时间守恒，打印结果并更新 `reference_case_checks.json`。它不生成计划，也不访问任何邮箱或日历账户。

### 风险和假设

| 风险或假设 | 应对与验证 |
| --- | --- |
| 日期提取可能错误 | 原文可追溯，学生确认前不排程 |
| 日历可能不完整，学校权限可能不可用 | 支持手动空闲与占用；如实报告接入状态 |
| 学生可能低估用时 | 更新剩余工作量后预览重排，容量不足返回缺口 |
| 普通学习任务能够拆分 | 报告、复习按短段处理；考试和会议作为固定占用 |
| 空闲时间代表学生愿意学习 | 学生可缩窄可用时间，不能把所有空闲都视为工作时间 |
| 初始参数是否合理 | 与全组确认，后续记录用户反馈，不宣称已有最佳参数 |

### 约一分钟的英文稿

“My component turns confirmed tasks and calendar gaps into a study plan. After the LLM extracts a task, the student confirms its deadline and estimated effort. A rule-based tool then schedules work within available hours, limits daily load, and keeps work before its deadline. A 24-hour buffer is a preference. When capacity is insufficient, the plan shows the missing hours.

For Sprint 1, we have specified the rules and checked five manually authored reference plans. Our normal example fits 7.5 hours. Another has nine hours of work but only three available, so it reports a six-hour shortage. The scheduler and calendar integration are still planned. Sprint 2 will implement scheduling and replanning, then test for conflicts, overload and work after deadlines.”

会议中文说法：“我准备了三个任务共七个半小时的手排方案，每天最多三小时，全部在截止前至少二十四小时完成。我还准备了九小时任务只有三小时空档的反例，应明确显示六小时缺口。会后我会和技术同学一起实现，并检查不撞课、不超载、不越过截止，以及重新排程是否保留锁定安排。”
